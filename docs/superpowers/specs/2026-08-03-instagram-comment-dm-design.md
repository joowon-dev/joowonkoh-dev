# 인스타그램 댓글 → DM 자동화 설계

경로: `/admin/instagram` (어드민), `/api/instagram/*` (웹훅·워커)

## 무엇을 만드는가

인스타그램 게시물에 댓글이 달리면, 그 사람에게 자동으로 DM을 보낸다. 지금 손으로 하루
1000건씩 처리하고 있는 일이다.

보내는 링크는 댓글 내용에 따라 다르다. "링크"라고 쓴 사람과 "가격"이라고 쓴 사람에게
같은 걸 보낼 수는 없다. 그래서 **키워드 → 링크** 매핑이 이 시스템의 핵심 설정값이고,
그 매핑을 어드민에서 관리한다.

## 왜 직접 만드는가

ManyChat 같은 SaaS로도 되지만 **컨택 수 과금**이다. 하루 1000건이면 월 3만 컨택이고,
Business 플랜 $69에 초과분 22,500명 × $0.018을 더하면 **월 $470, 한화 65만원**이다.
부수입을 만들려는 채널의 고정비로는 말이 안 된다.

직접 만들면 Supabase와 배포 플랫폼 무료 티어 안에서 끝난다. 대신 Meta 앱 검수를
통과해야 하고, 초기 세팅에 며칠이 든다. 그 거래가 이 규모에서는 명백히 남는다.

## 전체 흐름

```
① 댓글 웹훅 (comments)
      ↓  서명 검증 → 큐에 적재 → 즉시 200
   send_queue
      ↓  워커가 속도 조절하며 꺼냄
② 공개 답글  +  오프닝 DM (버튼 1개, 링크 없음)
      ↓
   사용자가 버튼 클릭
      ↓
③ postback 웹훅 → 키워드에 맞는 링크 DM
```

### 왜 두 단계로 나눠 보내는가

한 번도 나에게 DM을 보낸 적 없는 사람에게 보낸 메시지는 인스타그램의 **"요청(Requests)"
폴더**로 들어간다. 상대가 그 폴더를 열지 않으면 그냥 묻힌다. 거기에 링크만 덜렁 있으면
스팸으로 보여서 더 열지 않는다.

그래서 첫 DM에는 링크를 넣지 않는다. 버튼 하나만 놓고, 상대가 그걸 누르면 대화가 일반
받은편지함으로 옮겨가고 **24시간 메시징 창**이 열린다. 그 창 안에서 링크를 보낸다.

링크 전달이 한 단계 늦어지는 대신, 요청 폴더에서 썩지 않는다.

오프닝 DM 문구는 팔로우 요청을 겸한다.

> 안녕하세요! 이 링크는 팔로워분들께만 제공되는 링크입니다.
>
> 아직 팔로우 안 하셨다면 한 번만 눌러주시면 감사하겠습니다 😊

버튼 레이블은 `팔로우했어요, 링크 주세요 🔗`.

## 왜 큐를 두는가

웹훅을 받은 자리에서 바로 DM을 보내면 두 군데서 깨진다.

**첫째, Meta의 웹훅은 빨리 200을 받지 못하면 재전송한다.** 그 자리에서 API를 두세 번
호출하고 있으면 응답이 늦어지고, 재전송된 웹훅이 같은 댓글을 또 처리한다.

**둘째, 발송량이 우리 손을 떠난다.** 릴스 하나가 터져서 1분에 200개 댓글이 달리면
그대로 200건을 쏜다. Private Reply 한도는 시간당 750건이고, 넘으면 조용히 실패한다.
그보다 먼저 Meta의 스팸 탐지에 걸린다.

그래서 웹훅 핸들러는 **검증하고 큐에 넣고 200을 반환하는 것까지만** 한다. 실제 발송은
워커가 정해진 속도로 꺼내서 한다. 이 분리가 이 설계에서 가장 중요한 부분이다.

워커는 Supabase `pg_cron`이 1분마다 `pg_net`으로 `/api/instagram/worker`를 호출해서
돌린다. 배포 플랫폼의 크론 기능에 의존하지 않으므로 Vercel이든 Cloudflare든 상관없다.

## 데이터 모델

### `ig_keyword_rules` — 키워드 매핑

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid | |
| `keyword` | text | 소문자로 정규화해서 저장 |
| `link_url` | text | 보낼 링크 |
| `message_template` | text | 링크와 함께 보낼 문구 |
| `priority` | int | 여러 키워드가 걸릴 때 낮은 값이 이김 |
| `enabled` | bool | |

매칭은 **포함(contains)** 방식이다. 정확히 일치로 하면 "링크요~", "링크 주세요"를 전부
놓친다. 댓글을 소문자로 바꾸고 공백을 정리한 뒤 `keyword`가 들어있는지 본다.

여러 규칙이 동시에 걸릴 수 있다. "링크랑 가격 알려주세요" 같은 댓글이 그렇다. 이때는
`priority`가 낮은 것 하나만 쓴다. 둘 다 보내면 DM이 두 통 가고, 그게 스팸 신호다.

### `ig_comments` — 처리한 댓글

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `comment_id` | text **unique** | 인스타 댓글 ID |
| `media_id` | text | 게시물 ID |
| `ig_user_id` | text | 댓글 작성자 |
| `text` | text | 댓글 원문 |
| `matched_rule_id` | uuid null | 걸린 규칙. null이면 무매칭 |
| `created_at` | timestamptz | |

`comment_id`의 유니크 제약이 **중복 발송을 원천 차단하는 장치**다. Meta 웹훅은 같은
이벤트를 두 번 이상 보낼 수 있고, 워커도 재시도한다. 애플리케이션 코드로 "이미 처리했나"를
확인하면 동시에 들어온 두 요청이 둘 다 통과하는 순간이 생긴다. DB 제약이면 그 순간이 없다.

삽입이 충돌하면 그냥 무시하고 200을 반환한다. 그게 정상 동작이다.

### `ig_send_queue` — 발송 대기열

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | uuid | |
| `comment_id` | text | |
| `kind` | text | `opening` \| `link` |
| `status` | text | `pending` \| `sent` \| `failed` \| `expired` |
| `scheduled_at` | timestamptz | 이 시각 이후에 보낸다 |
| `attempts` | int | |
| `last_error` | text | |
| `expires_at` | timestamptz | 댓글 시각 + 7일 |

Private Reply는 **댓글 하나당 딱 한 번, 댓글이 달린 지 7일 이내**만 가능하다. 큐가 밀려서
7일을 넘긴 항목은 보내봤자 실패하므로 `expired`로 정리한다.

재시도는 3회까지, 지수 백오프(1분 → 5분 → 25분)로 한다. 3회 실패하면 `failed`로 두고
어드민에서 보이게 한다. 자동으로 무한 재시도하면 Meta 쪽에 우리가 고장난 클라이언트로 보인다.

### `ig_contacts` — 사람별 진행 상태

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `ig_user_id` | text **unique** | |
| `stage` | text | `opened` \| `clicked` \| `delivered` |
| `first_seen_at` | timestamptz | |
| `last_sent_at` | timestamptz | |

같은 사람이 여러 게시물에 댓글을 달 수 있다. 그때마다 오프닝 DM을 새로 보내면 도배가
된다. 이미 `clicked` 이상인 사람에게는 오프닝을 건너뛰고 링크 DM으로 바로 간다.

### `ig_message_variants` — 문구 변형

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `kind` | text | `public_reply` \| `opening` |
| `body` | text | |
| `enabled` | bool | |

**똑같은 문구를 대량으로 보내는 것이 스팸 판정의 가장 큰 신호다.** 공개 답글과 오프닝 DM은
발송할 때마다 활성 변형 중 하나를 무작위로 고른다. 각각 3~5개를 넣어둔다.

## 발송 속도와 램프업

`ig_settings` 테이블에 단일 행으로 둔다.

| 설정 | 초기값 | 설명 |
|---|---|---|
| `daily_limit` | 300 | 하루 발송 상한 |
| `hourly_limit` | 120 | 시간당 상한 |
| `paused` | false | 긴급 정지 |

시간당 750이 Meta의 기술적 상한이지만, 그것과 별개로 갑자기 하루 1000건을 쏘는 계정은
스팸 탐지에 걸린다. **2~3주에 걸쳐 300 → 1000으로 올린다.** 자동으로 올리지 않는다 —
어드민에서 손으로 올린다. 계정 상태를 보면서 판단해야 하는 값이라 자동화할 대상이 아니다.

`paused`는 뭔가 잘못됐을 때 한 번에 멈추는 스위치다. 코드 배포 없이 멈출 수 있어야 한다.

상한에 걸린 항목은 버리지 않고 `scheduled_at`을 다음 시간대로 밀어둔다.

## 무매칭 댓글

어떤 키워드에도 걸리지 않는 댓글은 **기록만 하고 아무것도 보내지 않는다.**

"좋아요", "잘 봤습니다" 같은 일반 댓글에 DM을 보내면 그게 진짜 스팸이다. 대신
`ig_comments`에 `matched_rule_id = null`로 남겨서, 어드민에서 무매칭 댓글 목록을 볼 수
있게 한다. 거기서 "이 표현도 키워드로 추가해야겠다"를 발견하는 것이 이 기록의 목적이다.

## 어드민 화면

`/admin/instagram`, 네 개 탭이다.

**키워드** — 규칙 CRUD. 키워드, 링크, 문구, 우선순위, 활성 여부. 새 키워드를 넣을 때
기존 규칙과 겹치는지(한쪽이 다른 쪽을 포함하는지) 경고한다.

**대기열** — 오늘 발송 현황, `pending`/`failed` 목록, 실패 사유. 실패 건 수동 재시도.

**설정** — `daily_limit`, `hourly_limit`, `paused`. 문구 변형 관리.

**무매칭** — 키워드에 걸리지 않은 최근 댓글. 여기서 바로 키워드로 승격할 수 있다.

### 어드민 인증

이 사이트는 공개 블로그다. `/admin` 아래는 반드시 막아야 한다.

환경 변수의 비밀번호 하나로 로그인하고, 서명된 httpOnly 쿠키를 준다. 미들웨어에서
`/admin/*`과 `/api/admin/*`을 검사한다. 사용자가 한 명뿐이므로 Supabase Auth를 붙이는 것은
과하다. 로그인 시도는 IP 기준으로 분당 5회로 제한한다.

## Meta 권한과 앱 검수

필요한 권한은 넷이다.

- `instagram_basic`
- `instagram_manage_comments` — 댓글 웹훅 수신, 공개 답글
- `instagram_manage_messages` — DM 발송
- `pages_manage_metadata` — 웹훅 구독

이 중 뒤의 셋은 **앱 검수(App Review)** 대상이다. 화면 녹화와 사용 사례 설명을 제출하고
며칠에서 2주가 걸린다. **개발 시작과 동시에 신청을 걸어두는 것**이 일정상 중요하다.
검수를 기다리는 동안 개발자 본인 계정으로는 테스트가 가능하다.

## 환경 변수

기존에 `NEXT_PUBLIC_SUPABASE_URL`과 `NEXT_PUBLIC_SUPABASE_ANON_KEY`가 있다. 여기에 더한다.

| 변수 | 용도 |
|---|---|
| `SUPABASE_SERVICE_ROLE_KEY` | 서버 전용. 인스타 테이블 접근 |
| `IG_APP_SECRET` | 웹훅 서명 검증 |
| `IG_VERIFY_TOKEN` | 웹훅 등록 시 challenge |
| `IG_ACCESS_TOKEN` | 장기 페이지 액세스 토큰 |
| `IG_BUSINESS_ACCOUNT_ID` | |
| `WORKER_SECRET` | pg_cron → 워커 호출 인증 |
| `ADMIN_PASSWORD` | 어드민 로그인 |

기존 `supabaseClient.ts`는 anon 키로 브라우저에서 쓰는 클라이언트다. 인스타 테이블은
**서버에서만** 접근하므로 `src/lib/supabaseAdmin.ts`를 따로 만들어 service role 키를 쓴다.
이 파일은 절대 클라이언트 컴포넌트에서 import되지 않아야 한다.

인스타 테이블 전체에 RLS를 켜고 anon 역할에 정책을 주지 않는다. service role은 RLS를
우회하므로 서버는 그대로 동작하고, 브라우저에서는 아무것도 보이지 않는다.

## 보안

**웹훅 서명 검증이 없으면 누구나 우리 API를 호출해서 아무 사람에게나 DM을 보낼 수 있다.**
Meta는 `X-Hub-Signature-256` 헤더에 앱 시크릿으로 서명한 HMAC을 보낸다. 이걸 **원문
바디**로 검증한다. JSON으로 파싱한 뒤 다시 문자열로 만들면 바이트가 달라져서 검증이
깨진다. Next.js Route Handler에서 `await req.text()`로 받아 검증하고, 그 문자열을 파싱한다.

비교는 상수 시간 비교(`crypto.timingSafeEqual`)를 쓴다.

워커 엔드포인트도 `WORKER_SECRET` 헤더로 막는다. 뚫리면 발송 속도 제어가 무의미해진다.

## 모듈 경계

| 파일 | 역할 | 외부 의존 |
|---|---|---|
| `src/lib/instagram/matcher.ts` | 댓글 텍스트 + 규칙 → 매칭 결과 | 없음 (순수 함수) |
| `src/lib/instagram/rateLimit.ts` | 지금 몇 건 보낼 수 있는가 | 없음 (순수 함수) |
| `src/lib/instagram/api.ts` | Meta Graph API 호출 | fetch |
| `src/lib/instagram/queue.ts` | 큐 적재·조회·상태 전이 | Supabase |
| `src/app/api/instagram/webhook/route.ts` | 웹훅 수신 | 위 모듈들 |
| `src/app/api/instagram/worker/route.ts` | 큐 소비 | 위 모듈들 |

`matcher.ts`와 `rateLimit.ts`를 순수 함수로 떼어내는 이유는 **이 둘이 틀리면 사고가
크기 때문**이다. 키워드가 잘못 걸리면 엉뚱한 링크가 나가고, 속도 계산이 틀리면 계정이
정지된다. 그런데 이 두 가지는 인스타 API도 DB도 필요 없다 — 입력과 출력만 있다.
분리해두면 Vitest로 전부 검증할 수 있다. 이 프로젝트는 이미 Vitest를 쓰고 있다.

## 테스트

순수 함수 쪽을 집중적으로 덮는다.

**matcher** — 대소문자, 조사 붙은 형태("링크요", "링크 주세요"), 여러 규칙 동시 매칭 시
우선순위, 무매칭, 비활성 규칙 제외.

**rateLimit** — 일일/시간당 상한 도달, 경계값, `paused` 상태, 다음 슬롯 계산.

**서명 검증** — 유효한 서명 통과, 변조된 바디 거부, 헤더 없음 거부.

**중복 처리** — 같은 `comment_id` 두 번 삽입 시 두 번째가 발송을 만들지 않는 것.

## 만들지 않는 것

- **AI 답변 생성.** 링크는 정해진 것을 보낸다. LLM을 끼우면 비용과 지연과 사고 가능성만 는다.
- **팔로워 여부 실제 검증.** 인스타 프로필 조회에 `is_user_follow_business` 필드가 있어
가능해 보이지만 확인이 필요하다. 1차에서는 문구로만 유도하고, 검수 통과 후 실제 응답을
보고 붙일지 정한다.
- **다중 계정 지원.** 계정은 하나다.
- **통계 대시보드.** 대기열 화면의 숫자로 충분하다. 필요해지면 그때 만든다.
- **댓글 스레드 대화.** 링크 하나 주는 것으로 끝이다.

## 확인이 필요한 것

**`is_user_follow_business` 필드의 실제 동작.** 문서상 존재하지만 권한과 조건을 확인하지
못했다. 팔로워 조건부 발송의 가능 여부가 여기에 달려 있다.

**배포 플랫폼.** `wrangler.toml`과 `@cloudflare/next-on-pages`가 있어 Cloudflare Pages로
보이지만, 실제 운영 배포처를 확인해야 한다. 워커를 `pg_cron`으로 돌리는 선택이 이
불확실성을 대부분 흡수하지만, Node 런타임 API(`crypto`)를 쓰므로 엣지 런타임이면
`export const runtime = "nodejs"`가 필요하다.
