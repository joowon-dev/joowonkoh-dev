# 코인 푸셔 추첨기 (Coin Pusher) — 설계

작성일: 2026-07-28
경로: `/playground/coin-pusher`

## 1. 목적

참가자 이름을 붙여넣으면 오락실 코인 푸셔 기계 위에서 각자의 코인이 떨어지고, 푸셔에 밀려 가장 먼저 낭떠러지 아래로 떨어진 코인의 주인이 당첨되는 추첨기. 모임·회식·경품 추첨에서 화면을 띄워놓고 돌리는 용도.

기존 `/playground/paper-plane`이 만들어 둔 "센서·물리 기반 미니게임 + 순수 함수 물리 모듈 + vitest" 패턴을 이어간다.

## 2. 게임 흐름

상태 머신: `setup → dropping → pushing → result`

**구현 편차:** 실제 구현에서는 `dropping`과 `pushing`이 `"playing"` 하나의 phase로 합쳐졌다
(`CoinPusherGame.tsx`의 `Phase` 타입). 두 단계는 큐가 비었는지(`allDropped()`) 여부로만
갈리기 때문에 별도 phase로 나눌 실익이 없다고 판단했다.

1. **setup** — 참가자 이름 입력. 줄바꿈 또는 쉼표 구분 텍스트를 붙여넣으면 칩 목록으로 파싱. 공백 제거, 중복 제거, 빈 문자열 제외.
2. START 시 판은 비어 있다. 미리 배치하지 않고, 중립 코인이 미는 판 위로 약 7초에 걸쳐 우르르 쏟아지면서 더미를 만든다. 개수는 참가자 수에 비례하되 80~170개.
3. **dropping** — 중립 코인 투하가 끝나면 참가자 코인 **전원이 같은 순간에 한꺼번에** 미는 판 위로 쏟아진다. 순차 투입은 §5.5를 보라 — 구조적으로 불공정하다.
4. **pushing** — 푸셔가 앞뒤로 왕복하며 코인 더미를 민다. 중립 코인이 일정 간격으로 추가 투입된다. 이 단계에서 돌발 이벤트가 확률적으로 발생하고, 경과 시간이 임계값을 넘으면 막판 스퍼트로 전환된다.
5. **result** — 첫 참가자 코인이 앞 낭떠러지 아래로 떨어지는 순간 슬로우모션 → 당첨자 발표.

**투입 지점:** 모든 코인은 미는 판(푸셔 상판) 위에 떨어진다. 판이 뒤에서 앞으로 갈수록 넓어지므로, 코인은 좁은 뒤쪽에 쌓였다가 밀려 나오면서 부채꼴로 퍼진다.

**결과 전환 시점:** "떨어지는 코인이 하나도 없을 때"로 판단하면 안 된다. 중립 코인이 계속 떨어지고 있어 그 순간이 오지 않는다. 당첨 시각으로부터 낙하 연출 시간만큼 지났는지로 판단한다(`CoinPusherGame.tsx`의 `wonAtRef`).

**낙하문(Gate):** 낙하선 앞은 대부분 벽이고, 판 앞쪽 너비의 30%만 열려 있다. 이 열린 구간이 좌우로 계속 왕복하며, 코인은 그 구간에 있을 때만 떨어진다. 코인이 앞줄에 쌓였다가 문이 지나갈 때 한 번에 쏟아지므로 순위가 계속 뒤집힌다. 벽은 반드시 그려야 한다 — 안 그리면 코인이 보이지 않는 무언가에 막혀 쌓이는 것처럼 보인다.

**당첨 규칙:** 먼저 떨어진 코인 1명. 같은 프레임에 여러 코인이 낙하 조건을 만족하면 낙하선을 더 많이 넘어선(worldY가 더 큰) 코인이 승리한다. 부동소수점이 완전히 같은 경우는 배열 인덱스가 작은 쪽으로 결정론적으로 처리한다.

## 3. 시점과 렌더링

물리는 순수 2D 평면 `(x, y)`에서 계산하고, 렌더링 단계에서만 비스듬한 시점으로 왜곡한다.

- 화면 좌표: `screenY = worldY * PERSPECTIVE_SCALE` (0.72)
- 판이 사다리꼴이라 좌우 벽이 원근선처럼 모여, 별도의 x 왜곡 없이도 입체로 읽힌다
- 배율에는 상한(`MAX_SCALE`)이 있다. 판이 좁고 깊어서 큰 화면에서 폭에 맞추면 코인 하나가 100px을 넘고 판이 코인 몇 개 폭처럼 보인다. 상한을 넘으면 남는 공간은 여백으로 두고 가운데 정렬한다.
- 코인은 원 + 아래쪽으로 두께만큼 그린 실린더 옆면 + 바닥 그림자로 입체감 표현
- 앞 가장자리 아래로 떨어지는 구간은 물리 시뮬레이션에서 분리해 **순수 연출**로 처리 (회전하며 낙하)
- Canvas 2D, `devicePixelRatio` 대응
- 3D 라이브러리를 도입하지 않는다

## 4. 물리 — 자체 구현

### 근거
모든 코인이 동일 반지름의 원이라 필요한 충돌 처리는 원-원과 원-AABB뿐이다. Matter.js를 도입하면 번들이 늘고, 회전을 포함한 일반 강체 해법은 이 게임에 과하다. 종이비행기가 이미 순수 함수 물리 모듈 + vitest 패턴을 쓰고 있어 일관성도 맞다.

### 모델
- 코인: 위치 `(x, y)`, 속도 `(vx, vy)`, 반지름, 질량, 반발계수. 참가자 코인은 반지름이 전부 14로 같고, 중립 코인은 10 / 14 / 19 세 가지 중 하나를 무작위로 받는다. 질량은 반지름²에 비례한다. `spin`은 렌더 전용 회전각으로 물리에 영향을 주지 않는다.
- 푸셔: 뒤에서 앞으로 왕복하는 이동 AABB
- 판: 뒤에서 앞으로 갈수록 넓어지는 사다리꼴. 좌우 벽 위치는 깊이의 함수(`halfWidthAt`)이고, 앞은 열린 낭떠러지다. x 좌표계는 `0..width`이며 기준선은 `centerX`.

### 크기가 다른 코인이 건드리는 곳
반지름이 상수가 아니게 되면서 다음이 전부 코인별 반지름을 쓴다: `resolvePair`의 최소 거리, `clampToWalls`의 벽 여유, `applyPusher`의 앞면 여유, `candidatePairs`의 접촉 판정. 공간 해시 셀 크기는 **가장 큰 코인**의 지름(`MAX_COIN_RADIUS * 2`) 이상이어야 하며, 그보다 작으면 큰 코인 쌍이 조용히 누락된다.

### 스텝
고정 타임스텝 `1/120초`를 누적기(accumulator)로 소비한다. 렌더 프레임레이트와 무관하게 결정론적이므로, 시드가 같으면 결과가 재현된다.

각 스텝 순서:
1. 푸셔 위치 갱신
2. 코인-코인 충돌: 위치 보정(penetration resolution) + 임펄스
3. 코인-벽, 코인-푸셔 충돌
4. 마찰 감쇠
5. 낙하 판정 (`y > FALL_LINE`)

### 성능
공간 해시 그리드로 브로드페이즈를 O(n)에 처리한다. 참가자 40명(코인 약 80개) 기준 60fps를 목표로 한다.

**참가자 상한 40명의 근거:** 로스터 크기별로 시드를 바꿔가며 실제 게임 루프를 돌려 측정한 결과,
4~40명 전 구간에서 12~47초 안에 당첨자가 나오고 당첨 시점에 대기 중인 참가자는 0%였다. 판 위
코인은 최대 124개에서 포화한다. 이 선을 넘기면 투입 순서가 늦은 참가자는 코인이 판에 오르기도
전에 게임이 끝나 당첨 확률이 0에 가까워지므로, 40은 성능 상한이 아니라 §5.5 공정성을 지키기
위한 공정성 상한이다. `SetupPanel.tsx`의 `MAX_PLAYERS`도 이 값을 반영한다. 판 크기·투입 속도를
바꾸면 이 값을 다시 측정해야 한다.

**실측(300판씩):** 당첨자 분포 χ² = 17.5 / 18.5 / 36.5 (8·20·40명, 자유도 n-1),
시작 등수별 분포 χ² = 8.8 / 17.5 / 40.0 — 둘 다 균등과 일관된다.
소요 시간은 8명 23~34초, 20명 19~32초, 40명 12~24초. 판 위 코인은 최대 175개.

### 난수
시드 기반 PRNG(mulberry32 등)를 물리·이벤트 전 구간에서 사용한다. `Math.random()`을 직접 호출하지 않는다. 시드는 게임 시작 시 한 번 생성한다.

## 5. 랜덤 요소

### 5.1 초기 배치·투입 랜덤
- 중립 코인의 초기 좌표와 개수
- 참가자 코인의 낙하 순서, 낙하 지점, 초기 속도

### 5.2 중립 코인의 크기
중립 코인은 크기 3종(10 / 14 / 19)을 무작위로 받고, 크기마다 색이 조금씩 다르다(작을수록 밝다). 질량은 반지름²에 비례한다.

특수 능력을 가진 코인은 없다. 한때 폭탄·순간이동 이벤트 코인을 넣었다가 화면이 산만해서 걷어냈다. 되살릴 생각이라면 알아둘 것: 폭탄이 더미를 흔들어 교착을 깨고 있었기 때문에, 없애자 게임이 눈에 띄게 길어졌다(8명 기준 중앙값 28초 → 45초). 중립 코인 투입 간격과 막판 스퍼트 시각을 다시 맞춰야 한다.

### 5.3 돌발 이벤트
`pushing` 단계에서 확률적으로 발생하며, 상단 배너로 표시된다.
- 진동: 이벤트가 지속되는 0.4~0.9초 동안 매 스텝 전체 코인에 무작위 방향의 작은 임펄스를
  다시 적용한다(`events.ts`의 `applyScheduler`). 한 번의 단발 임펄스가 아니라 짧게 이어지는
  떨림으로 구현했다 — 시각적으로 더 자연스러운 "흔들림"이 되기 때문이며, 매 스텝 크기를
  0.02배로 줄여 발산하지 않는다.
- 판 기울기: 일정 시간 동안 한쪽 방향 가속도 추가
- 푸셔 러시: 푸셔 왕복 속도 2배
- 역류: 1~2초 동안 판 전체에 뒤쪽 가속도를 준다. 앞줄에 붙어 있던 코인이 가장 크게 손해를 본다.
- 출구 가속: 낙하문이 2~3배 빠르게 왕복한다.
- 융기: 판 위 한 지점이 솟구쳐 반경 130 안의 코인을 바깥으로 날린다. **더미의 순서를 실제로 뒤섞는 유일한 힘이다** — §5.6 참고.

### 5.4 막판 스퍼트
경과 30초 시점부터 푸셔 스트로크를 확대하고 중립 코인을 대량 투하해 교착을 강제로 깬다.

### 5.5 예측 불가능성 — 시작 위치가 결과를 정하면 안 된다

공정한 것과 재미있는 것은 다르다. 참가자마다 좋은 자리를 받을 확률이 같으면 추첨으로서는 공정하지만, 자리가 정해지는 순간 승자가 사실상 결정돼 버리면 보는 재미가 없다.

코인 더미는 통째로 밀려가는 컨베이어에 가까워서 **시작 깊이 순서가 끝까지 거의 그대로 보존된다.** 참가자 코인을 격자로 여러 줄에 세웠더니 20명 기준으로 뒷줄 출발이 앞줄 출발보다 10배 넘게 이겼다(앞 1/4 승률 8%, 균등이면 25%). 낙하문과 융기 이벤트를 넣어도 이 편향은 거의 그대로였다 — 원인이 이벤트 부족이 아니라 배치 구조였기 때문이다.

해결은 **참가자 코인 전원을 같은 깊이에 세우는 것**이다(`setup.ts`의 `scatterSpots`). 구조적 예측 인자가 사라지고 더미의 혼돈이 승부를 가린다. 측정 결과 앞 1/4 승률이 8% → 24%(균등 25%)로 회복됐고, 시작 등수별 분포도 균등해졌다(χ² = 17.5, 자유도 19).

깊이를 다시 여러 줄로 바꾸면 이 편향이 조용히 되살아난다.

### 5.6 공정성
참가자 코인은 질량·반지름·마찰·반발계수가 전부 동일하고, 시작 자리만 랜덤이다. 특수 능력을 가진 코인은 없다.

**순차 투입은 불공정하다.** 먼저 들어온 코인이 그만큼 더 오래 밀리기 때문이다. 실측(300판): 20명 기준 1등 투입 34승 / 꼴찌 투입 0승, 앞 절반 승률 76% (χ²=138.7, df=19). 그래서 참가자 코인은 전원 같은 순간에 투입한다.

**동시 투입만으로도 부족하다.** 같은 시각의 코인들은 큐 순서대로 `world.coins`에 들어가고, 충돌 해소(`candidatePairs` → `resolvePair`)가 그 배열 순서대로 돈다. 겹쳐서 시작한 무리에서는 배열 앞쪽 코인이 체계적으로 다르게 밀리므로, 참가자 번호 순으로 넣으면 그대로 편향이 된다(40명에서 χ²=220, 300판 중 한 번도 못 이긴 참가자 발생). `setup.ts`에서 참가자 순서를 섞어 **배열 위치와 시작 자리 둘 다** 참가자와 무관하게 만든다. 이 셔플을 지우면 편향이 조용히 되살아난다.

이 공정성은 판이 포화하지 않는 범위(§4 성능의 40명 상한 참고)에서만 성립한다. 로스터가 판 용량을
넘으면 낙하 순서가 늦은 참가자는 코인이 판에 오르기도 전에 게임이 끝나 당첨 확률이 사실상 0이 되므로,
UI 단(`SetupPanel.tsx`의 `MAX_PLAYERS`)에서 40명으로 상한을 둔다.

## 6. UI

- 상단 HUD: 남은 인원 수, 경과 시간, 진행 중인 이벤트 배너
- 낙하문: 닫힌 구간은 앞 가장자리에 벽으로, 열린 구간은 accent 색 글로우로 그린다
- 코인 위에 참가자 이름 라벨. 코인이 겹치면 최상단 코인의 라벨만 그린다. (구현 메모:
  명시적인 오클루전 컬링은 없다. `render.ts`의 `drawScene`이 코인을 뒤에서 앞 순서로 그리면서
  앞 코인이 뒤 코인의 라벨을 페인터 알고리즘으로 덮어 가리는 방식이라, 완전히 겹칠 때는
  스펙대로 보이지만 부분적으로만 겹칠 때는 가려진 라벨의 일부가 삐져나와 보인다. 이 정렬
  순서를 "정리"하면 라벨이 이상하게 보이는 회귀가 생기니 주의할 것.)
- 하단 컨트롤: 스킵 버튼 하나. 누르면 시뮬레이션을 빠르게 진행해 즉시 결과로 간다.
- 당첨 연출: 슬로우모션 → 풀스크린 오버레이 + 컨페티 + 이름 크게 표시 → "다시하기" / "참가자 수정"
- 사이트 디자인 토큰(`accent`, `card-bg`, `border`, `text-primary` 등) 재사용. 다만 판 바닥은 흰 배경 위에서 형태가 보여야 하므로 카드 배경 대신 고정 회색조를 쓴다.
- 플레이 화면은 뷰포트를 통째로 쓴다. 캔버스가 화면을 다 덮고 HUD와 버튼을 그 위에 얹으며, safe-area를 보정한다.
- 애니메이션: 코인 투입 시 위에서 내려앉기(그림자가 함께 커진다), 이동량에 비례하는 회전 각인, 낙하문 글로우, 융기 충격파 2겹, 흔들림·융기 이벤트 동안의 화면 흔들림.
- 돌발 이벤트는 상단 배너로 알린다.

## 7. 데이터 저장

## 9. 테스트

vitest 대상은 순수 모듈에 한정한다.
- `physics.ts`: 두 코인 충돌 후 운동량 보존, 벽 관통 없음, 푸셔가 코인을 앞으로 민다, 낙하선 통과 시 낙하 판정, 같은 시드로 두 번 돌리면 동일 결과
- `events.ts`: 시드 고정 시 이벤트 발생 시퀀스 재현, 막판 스퍼트가 임계 시각에 활성화, 중립 코인 크기가 3종 안에서만 나옴
- `random.ts`: 같은 시드 → 같은 수열

Canvas 렌더와 React 컴포넌트는 단위 테스트하지 않는다.
